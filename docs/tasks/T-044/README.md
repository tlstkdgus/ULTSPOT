## 배경

클라우드 플래그를 켜고 프로덕션에서 현장 현황을 실제로 눌러봤다. 동의 모달·게스트 생성·
포인트(+20)까지 전부 의도대로였는데, **내가 고른 값과 다른 값이 화면에 떴다.**

`Medium` / `Plenty`를 골라 공유했는데 화면에는 `Queue: Long · Gifts left: All gone`이 나왔다.

## 원인

`place_status_summary`가 `group by o.pid, o.is_open, r.waiting, r.perks`로 집계한다.
즉 **서로 다른 답이 올라온 만큼 장소당 행이 쪼개진다.** 프로덕션에서 실제로 이렇게 왔다:

```
{place_id:"hikr-ground", waiting:"long",   perks:"none",   reports:1}
{place_id:"hikr-ground", waiting:"medium", perks:"plenty", reports:2}
```

화면은 `statuses.find(s => s.placeId === pid)`로 **첫 행만** 썼다. 결과적으로

- 1건짜리 답이 2건짜리 답을 가렸다
- 보고 수가 3이어야 하는데 1로 표시됐다

한 명이 올린 답이 스무 명의 답을 가릴 수 있는 구조였다.

## 결정

- **화면에서 합친다.** DB 함수를 고치면 마이그레이션을 또 적용해야 하는데, 이미 두 번
  부탁드렸다. 그리고 조합별 행은 분포 정보를 담고 있어 그 자체로 버릴 값이 아니다.
- **대표값은 가장 많이 보고된 조합.** 평균이나 최빈 단일 필드가 아니라 조합 단위로 고른다 —
  "대기 길고 특전 넉넉"처럼 함께 와야 말이 되는 값이라, 필드별로 최빈값을 뽑으면 아무도
  올리지 않은 조합이 만들어진다.
- **동점이면 먼저 온 쪽을 유지한다.** 새로고침할 때마다 표시가 흔들리지 않게 한다.
- **보고 수는 모든 행의 합.** 집계가 몇 건에 근거하는지가 신뢰도를 가른다.
- **모르는 값은 버리되 건수는 센다.** DB에 없는 선택지를 화면이 그리지 않게 하면서,
  보고가 있었다는 사실은 잃지 않는다.

## 하지 않은 것

- **DB 함수 변경** — 위 참조. 장소당 1행으로 줄이면 분포를 볼 길이 없어진다.
- **분포 전체를 화면에 보여주기** — "대기: 길다 1 · 보통 2" 같은 표시는 정보가 늘지만
  카드가 커지고, 지금 데이터 양(장소당 한자릿수)에서 얻는 게 적다. 값이 쌓이면 다시 본다.
