## 배경

PR #48로 들어온 팬 생일카페 3건이 `coord` 없이 있었다. `journey-planner.tsx:109`의
`pinned`가 `filter(p => !!p?.coord)`라 **좌표가 없으면 "이 날의 위치" 핀 목록에서 통째로
빠진다.** 이동시간도 좌표가 없으면 조회 자체가 불가능해 전 구간이 "좌표 미확인"이 된다.

즉 앱의 간판 데이터인 생일카페가 여정 화면에서 반쯤 죽어 있었다. 심사 기간이라 눈에 띄는
구멍부터 메운다.

## 결정

- **주소는 이미 있었다. 좌표만 변환했다.** 세 건 모두 수집본에 도로명 주소가 있다.
  `pnpm data:geocode`로 카카오 주소검색을 돌려 3/3 매칭했다.
- **운영시간은 채우지 않았다.** 조사 자료의 `unresolved`에 *"생일카페 원문 확인 0건.
  X robots 차단, 덕플레이스·오프메이트 목록 JS 렌더링"*으로 남아 있다. 근거 없이 시간을
  지어내면 심사자에게 틀린 일정을 보여주게 된다. `opens/closes`는 `null`로 두고 자동 편성
  제외 표시도 그대로 유지한다.
- **`coord.source`는 카카오이지 주최 공지가 아니다.** 좌표의 출처는 수집본이 아니므로
  `fan-cafes.ts` 헤더에 그 구분을 적었다. 좌표는 **주최자가 올린 주소만큼만 정확하고,
  건물을 가리키지 행사를 가리키지 않는다.** `k-star-road`가 이미 같은 방식이고 "거리 전체가
  약 1km라 이 좌표는 시작 지점 기준"이라는 주석을 달아둔 선례가 있다.
- **자동 반영하지 않았다.** `geocode.mjs`는 검수용 사이드카만 남기는 설계다. `review.json`의
  `matchedAddress`를 요청 주소와 대조하고, 좌표를 역지오코딩해 같은 도로명이 돌아오는지
  확인한 뒤에 손으로 넣었다.

## 함께 고친 것 — 지오코딩 확인일이 하루 빨랐다

`geocode.mjs`가 `new Date().toISOString().slice(0, 10)`으로 `checked_on`을 만들었다. UTC라
**KST 00:00~09:00 사이에 돌리면 어제 날짜를 데이터에 박는다.** 실제로 첫 실행에서
`2026-09-20`이 나왔다(실행 시각은 KST 9/21 새벽 2시). 출처의 확인일이 어긋나면 나중에
재확인 주기를 잘못 계산한다.

`intake.mjs:117`이 세션 날짜를 검증할 때 쓰는 `+9h` 보정과 같은 기준으로 맞췄다.
T-039에서 고친 `on-site-records.test.mjs`의 UTC/KST 버그와 정확히 같은 부류다 — 이 레포에서
세 번째다.

## 하지 않은 것

- **운영시간·예약·특전 채우기** — 원문 확인 0건. 위 참조.
- **`research-cli.mjs`와 API 라우트의 같은 UTC 패턴** — `scripts/catalog/research-cli.mjs:43`,
  `src/app/api/{recommend,travel}/route.ts`에 같은 `toISOString().slice(0,10)`이 있다. 지금은
  심사 기간이라 서버 라우트를 건드리지 않는다. 별건으로 남긴다.
- **일정(자동 편성) 화면 지도에 생일카페 띄우기** — 운영시간 미확인이라 자동 편성에서
  제외되는 것이 맞다. 좌표가 생겼다고 편성 자격이 생기지 않는다.
