## 배경

T-047 배포 후 프로덕션 검사에서 발자취 카드 검사가 mobile·tablet에서 깨졌다. 카드를 만드는 동안 서버
요청이 0건이어야 하는데 `/api/travel` 한 건이 잡혔다. 프로덕션에 대고 3회씩 반복하니 9번 중 2번 재현됐다.

카드가 부른 게 아니었다. 직전의 "다녀왔어요" 체크가 여정 객체를 바꾸고, 이동시간 조회 effect가
**여정 객체 전체**에 걸려 있어 다시 돌았다. 이동 구간(같은 날 이웃한 두 곳)은 그대로인데도 그랬다.
그 결과 체크인·지출·메모를 할 때마다 카카오 경로 API를 다시 불러 무료 쿼터를 썼다.

## 결정

- **조회를 구간 내용에 건다.** `journeyLegs(journey)`를 JSON 문자열로 메모이즈해 effect 의존성으로 쓴다.
  구간이 같으면 문자열이 같아 조회가 나가지 않는다. 방문 순서·날짜 이동·장소 추가처럼 구간이 실제로
  바뀌면 전처럼 조회한다.
- 조회 함수는 여정 대신 구간 배열을 받는다. 늦게 온 응답을 번호로 버리는 로직과 취소는 그대로다.

## 바뀐 검사

- `journey-ui.spec` "moving the last travel leg away clears a pending lookup"은 **"머무는 시간" 변경으로
  조회를 일으켰다.** 체류 시간은 구간을 바꾸지 않으므로 이제 조회가 나가지 않는 게 맞다. 순서 바꾸기
  ("Move later")로 구간을 바꿔 조회를 일으키게 고쳤다. 검사의 뜻(대기 중 조회가 구간 0개가 되면 풀린다)은 그대로다.
- 신규: "checking in and recording spending do not look up travel times again" — 첫 조회가 끝난 뒤부터
  체크인·지출을 해도 `/api/travel`이 0건이어야 한다.

## 하지 않은 것

- 조회 결과 캐시를 서버 쪽에서 더 늘리지 않았다. 불필요한 호출 자체를 없앴다.

## 알려진 문제 — 로컬 전체 실행의 fan-cafes mobile 포스터 대기

로컬 전체 E2E에서 `fan-cafes` mobile 포스터 검사가 간헐적으로(최근 4회 중 3회) 45초를 넘긴다. 확인한 것:

- 실패 트레이스에서 포스터 4장의 `/_next/image … w=828`(mobile DPR 2 전용 폭) 요청이 **응답도 실패도 없이
  대기**한다. 재시도 3번 모두 같다.
- 같은 빌드를 직접 띄운 서버에 w=828 요청 48건을 빈 캐시로 동시에 보내면 1초 안에 전부 200. 요청을
  중간에 끊은 뒤 다시 보내도 200. 서버 최적화기 자체는 멈추지 않는다.
- 직접 띄운 서버에 mobile 전체(116건)를 돌리면 전부 통과. Playwright가 띄운 서버로 돌릴 때만 간헐적으로 난다.
- 프로덕션(Vercel 이미지 서비스)에서는 check:prod 3회 모두 통과.

원인은 아직 특정하지 못했다. 프로덕션 사용자에게는 영향이 없다. 검사는 `retries: 2`로 두고, 다음에
재현되면 실패 트레이스의 네트워크 타임라인을 이 문서에 붙인다.
