## 배경 — "껍데기"의 실체

사용자가 "껍데기만 있는 것들을 해결하라"고 요청했다. 실제로 무엇이 비어 있는지 운영 환경에
직접 물어 확인했다.

| | 코드 | 운영 DB | 익명 auth | 프로덕션 플래그 | UI |
|---|---|---|---|---|---|
| 클라우드 저장(여행 계획) | 있음 | **적용됨** | **켜짐** | `false` | 있음 |
| 현장 기록 4개 테이블 | SQL만 | **없음** | — | — | 체크인·가계부는 기기 저장 |
| 포인트 · 공간 현황 | SQL만 | **없음** | — | — | **없음** |

`202609200002_on_site_records.sql`은 **서버 기반** 체크인(+10)·현황 리포트(+20)·포인트 원장
설계인데, T-038이 만든 체크인·가계부 UI는 **기기 저장 기반**이고 포인트가 없다. 인계 문서가
"체크인을 포인트 지급으로 표현하지 말라"고 지시했기 때문이다. 즉 DB와 UI가 서로 다른 방향을
보고 있었고, 포인트를 뺀 것은 사고가 아니라 결정이었다.

사용자가 이 방향을 뒤집어 "UI도 구현하되 로그인이 필요하면 모달이나 알림을 띄우라"고 정했다.

## 결정

- **서버로 가는 것은 공간 현황뿐이다.** 대기 정도·특전 잔여는 다른 팬에게 보여주려고 모으는
  값이라 브라우저에만 두면 집계가 성립하지 않는다. 반대로 체크인·가계부·발자취는 혼자 보는
  기록이라 기기 저장 그대로 두었다. 이 패널은 그것들을 **대체하지 않고 옆에 붙는다.**
- **익명 계정은 절대 조용히 만들지 않는다.** 사용자 지시를 그대로 구현했다. 버튼을 누르면
  먼저 모달이 뜨고, 무엇이 만들어지고(익명 게스트 id) 무엇이 저장되며(올린 장소와 포인트)
  무엇은 받지 않는지(이메일·비밀번호·이름) 읽게 한다. 취소하거나 Esc를 누르면 **요청이 한 건도
  나가지 않는다.** 이걸 E2E로 고정했다 — `/auth/v1/signup` 요청 수가 0이어야 통과한다.
- **포인트를 화면에서 계산하지 않는다.** +10/+20/-30, 하루 1회 제한, 중복 해제 방지는 전부 DB
  함수가 정한다. `point_ledger`는 클라이언트 쓰기 권한이 아예 없다. 이 패널은 함수를 부르고
  결과를 표시할 뿐이다.
- **DB 오류 원문을 그대로 보여주지 않는다.** 영어이고 내부 사정이 섞인다. `toCode()`로 분류해
  4개 언어 문구로 옮긴다.
- **select에 `aria-label`을 직접 달았다.** `<label>`이 `<select>`를 감싸는 기존 패턴은 접근성
  이름에 선택된 옵션 텍스트가 섞여 `getByLabel("Queue")`가 0건이 됐다. 이름을 요소에 박아 고쳤다.

## 하지 않은 것

- **운영 DB에 SQL 적용** — SQL Editor 접근 권한이 없어 수행할 수 없다. 사용자가
  [on-site-records.md §8](../../specs/on-site-records.md) 절차대로 1회 실행해야 이 화면이
  실제로 동작한다. **적용 전에는 패널이 떠 있어도 요청이 실패한다.**
- **프로덕션 클라우드 플래그 켜기** — 자동 승인 정책이 막아 사용자가 직접 바꾸기로 했다.
  플래그가 `false`면 이 패널은 "이 배포에서는 꺼져 있어요"만 보여주고 아무 요청도 하지 않는다.
- **기기 저장 체크인을 서버로 옮기기** — 로그인 없이 되는 핵심 흐름을 깨지 않는다. 서버 기록은
  "이 방문을 서버에도 기록 (+10)" 버튼으로 **선택**해서 추가한다.
- **닉네임·사진·자유 텍스트 후기** — 명세 §6이 모더레이션·스토리지·신고 계약이 없어 뺀 것이다.
  그 근거가 아직 유효하다.
- **GPS 체크인** — `record_checkin`은 `gps` 출처와 측정 거리를 받지만, 판정 반경의 근거가
  문서에 없어 `manual`만 쓴다. 명세 §6이 "반경은 DB에 넣지 않았다"고 적은 것과 같은 이유다.

## 검증

- typecheck 0, lint 오류 0 (경고 94건은 `.github/skills/` 벤더 JS로 무관)
- 데이터 테스트 **62건 통과 · 0 실패**
- E2E **312건 통과 · 3건 skip · 0건 실패** (390/768/1440 전부). 신규 15건:
  - 동의 전에는 `/auth/v1/signup` 요청이 0건이다
  - 공유 버튼을 누르면 모달이 뜨고, 그때까지도 요청은 0건이다
  - "나중에"와 Esc 모두 요청 0건으로 닫힌다
  - 선택지는 문서에 있는 4개씩만 나온다 (DB의 check 제약과 같은 값)
  - 게스트 없이도 체크인·가계부가 그대로 동작한다
- **운영 DB RLS 실검증 9건 통과** (이 브랜치 작업 전, `guest_trips` 대상):
  익명 사용자 A/B를 만들어 A가 B의 초안을 읽기·수정·삭제·위조 insert 시도 → 전부 차단,
  미인증 읽기/쓰기 → 401, B 초안 무손상 확인. 테스트 데이터는 삭제했다.

### 아직 검증하지 못한 것

**이 화면의 실제 동작은 검증되지 않았다.** 4개 테이블이 운영 DB에 없어 `record_status_report`·
`unlock_place`·`place_status_summary`를 한 번도 실제로 호출해보지 못했다. 위 E2E가 보증하는
것은 **요청을 보내지 않는 경로**(동의 전·취소·비활성)와 화면 구조까지다. PGlite 테스트 12건이
SQL과 정책이 의도대로 막는다는 것까지 보증하지만, 호스팅된 프로젝트에서의 동작은 별개다.

SQL 적용 후 확인해야 할 것:
1. 현황 공유 → +20점, 같은 날 재공유 시 +0점
2. 서버 기록 → +10점, 같은 장소 같은 날 재요청 시 +0점
3. 다녀오지 않은 장소 30점 해제, 잔액 부족 시 거부
4. 브라우저 A/B로 서로의 `point_ledger`·`place_checkins` 접근 차단
