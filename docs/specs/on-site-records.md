# 현장 기록 — 체크인·공간 현황·포인트·가계부

마이그레이션: `supabase/migrations/202609200002_on_site_records.sql`
검증: `node --test scripts/catalog/on-site-records.test.mjs` (12건, 실제 Postgres(PGlite)에서 실행)

이 문서는 [evidence-and-execution.md](evidence-and-execution.md)가 서버 저장의 전제로 요구한 **권한·동의·삭제 계약**이다. 계약 없이 테이블만 만들지 않기 위해 마이그레이션과 같은 커밋에 둔다.

## 1. 결정 C-12 개정 (2026-09-20)

[functional-spec.md](functional-spec.md) C-12와 §9.1 #3은 "여행 계획은 서버에 저장하지 않는다, 공유 링크는 제공하지 않는다"였다. 근거는 마감까지 만들 양을 줄이고 비로그인 사용자의 계획이 서버에 남지 않게 하는 것이었다.

**개정 내용은 좁다.** 여행 계획 본체는 그대로 브라우저에 남는다(`guest_trips`·`guest_journeys`는 지금도 사용자 1인 1초안 비공개다). 이 마이그레이션이 추가하는 것은 **팬이 현장에서 직접 남기기로 선택한 기록**뿐이다. C-12의 "계획을 서버에 두지 않는다"는 유지되고, "사용자가 남긴 현장 기록도 두지 않는다"로 확대 해석하지 않는다.

기존 문서와의 관계:
- [prd.md](prd.md) F-12와 [product-plan-v0.5.md](product-plan-v0.5.md) §7.1은 체크인·포인트·커뮤니티·가계부를 **P2 목업**으로 적었다. 이제 실제로 동작한다. 해당 표의 상태는 T-029 PR에서 함께 고친다.
- [functional-spec.md](functional-spec.md) §6.6 RLS 표의 "(여행 계획) 서버에 저장하지 않는다" 행은 그대로 맞다. 이 문서의 §3이 새 테이블 몫이다.
- 공유 링크와 공동 편집은 **아직 만들지 않았다**. §7 참조.

## 2. 무엇을 저장하고 무엇을 저장하지 않는가

| 저장한다 | 저장하지 않는다 |
|---|---|
| 방문한 장소 id와 날짜, 체크인 방식(`gps`/`manual`), gps일 때 측정 거리 | 좌표, 이동 경로, 실시간 위치 |
| 대기 정도·특전 잔여 (각각 선택지 4개) | 자유 텍스트 후기, 댓글 |
| 포인트 적립·차감 이력 | 등급, 뱃지 |
| 지출 금액(원), 날짜, 선택 시 장소, 메모 80자 | 결제수단, 영수증, 카드 정보 |
| — | 사진, 닉네임, 이름, 이메일, 전화번호 |

사진과 닉네임을 넣지 않은 이유는 §6에 있다.

## 3. 권한 모델

`anon` 역할은 네 테이블과 네 함수 전부에 접근할 수 없다. 익명 로그인 사용자는 `authenticated`이며, 아래가 그들에게 열린 전부다.

| 테이블 | 읽기 | 쓰기 |
|---|---|---|
| `place_checkins` | 본인 행만 | insert·delete만. **update 없음** — 체크인은 특정 순간의 기록이고, 고칠 수 있으면 기록이 아니다 |
| `place_status_reports` | **없음.** 직접 select 권한이 없다 | 본인 행만 insert·update·delete |
| `point_ledger` | 본인 행만 | **없음.** 클라이언트는 포인트를 쓸 수 없다 |
| `expenses` | 본인 행만 | 본인 행만 전체 |

핵심 두 가지:

- **포인트는 클라이언트가 못 쓴다.** `+10`(체크인)·`+20`(현황 공유)·`-30`(해제) 값은 `security definer` 함수 안에 있다. 브라우저가 스스로에게 지급하는 경로가 권한 수준에서 없다.
- **다른 사람의 현황은 행 단위로 읽히지 않는다.** `place_status_reports`에 select 권한을 주지 않고 `place_status_summary(place_ids)`로 **집계만** 돌려준다. `owner_id`가 응답에 들어가지 않으므로, 한 사람이 여러 장소를 돌아다닌 흔적을 이어 붙일 수 없다. 이건 [functional-spec.md](functional-spec.md) F-10이 공유 카드에서 "날짜별 정확한 방문 시각 포함 금지"로 이미 정한 원칙과 같은 방향이다.

함수 4개:

| 함수 | 하는 일 |
|---|---|
| `record_checkin(place_id, source, distance_m)` | 방문 기록 + 하루 한 번 `+10`. 같은 트랜잭션이라 방문 없는 적립이 생기지 않는다 |
| `record_status_report(place_id, waiting, perks)` | 현황 기록 + 하루 한 번 `+20`. 같은 날 수정은 반영되지만 추가 지급은 없다 |
| `unlock_place(place_id)` | 30점 차감. 이미 다녀온 곳과 이미 해제한 곳은 거부 |
| `place_status_summary(place_ids)` | 최대 50곳. 열린 곳은 선택지별 인원수, 잠긴 곳은 `open_to_me=false` 한 행 |

## 4. 남용 방지

익명 로그인은 계정을 무료로 만들 수 있다. 그래서 자유롭게 늘어나는 곳이 없어야 한다.

- 체크인·현황: **사용자 × 장소 × 날짜**가 기본 키라 하루에 한 행이 상한이다.
- 적립: 부분 유니크 인덱스 `point_ledger_one_award_per_day`. 체크인을 지우고 다시 해도 두 번 지급되지 않는다(원장은 append-only).
- 해제: `point_ledger_one_unlock_per_place`로 장소당 평생 1회.
- 지출: 유일하게 상한이 없는 테이블이라 트리거로 계정당 2,000행으로 막는다.
- 현황은 선택형이다. 다른 사람이 읽는 화면에 검수 못 한 문장이 올라가는 경로가 없고, 프롬프트 주입 경로도 없다([functional-spec.md](functional-spec.md) §8 보안 행과 같은 규칙).
- 장소 id는 `reviewed_place_id` 도메인으로 검수 카탈로그 슬러그만 받는다. `personal-`·`custom-`은 한 브라우저 안에만 있는 장소라 공유 기록을 만들면 구성원이 한 명이고 그 사람의 목록이 드러난다.

한계: 상한은 전부 계정 단위다. 계정을 여러 개 만드는 것 자체는 막지 못한다. 공개 배포 전에 [setup-cloud-trips.md](../setup-cloud-trips.md)가 이미 적어 둔 "봇 방어·사용량 제한"이 필요하고, 그건 이 마이그레이션이 해결하지 않는다.

## 5. 동의와 삭제

- 현장 기록은 **사용자가 그 순간 버튼을 눌러야만** 생긴다. 자동 수집·백그라운드 위치 조회는 없다.
- 위치는 체크인할 때 브라우저가 한 번 물어보고, 서버에 남는 것은 좌표가 아니라 거리(m)다. 거부해도 `manual` 체크인으로 진행할 수 있다.
- 삭제: 체크인·지출은 화면에서 지울 수 있다. 계정을 지우면 `on delete cascade`로 네 테이블의 모든 행이 함께 사라진다.
- **포인트 원장은 개별 삭제되지 않는다.** 적립 근거를 지우면서 잔액을 유지하면 장부가 거짓이 되기 때문이다. 계정 삭제 시에는 함께 지워진다. 이 점을 화면에 적는다.
- 현황 기록은 본인이 지울 수 있다. 다만 지우기 전에 다른 사람이 본 집계는 되돌릴 수 없다.
- [product-plan-v0.5.md](product-plan-v0.5.md) §5.4가 요구한 "수집 목적·활용 범위 명시"와 위치정보법 검토는 **아직 하지 않았다.** 데이터 판매(§5.2)는 이 계약의 범위가 아니고, 동의 문구 없이 켜면 안 된다.

## 6. 문서 근거가 없어 여기서 정한 값

아래는 어떤 기존 문서에도 근거가 없다. 물어볼 사람이 없어 정했고, 바꿔야 하면 이 표를 고친다.

| 항목 | 정한 값 | 왜 |
|---|---|---|
| 체크인 중복 방지 | 장소당 하루 1회 | 하루에 두 번 간 것과 두 번 누른 것을 구분할 방법이 없다 |
| 체크인 성립 | 위치(`gps`) 또는 수동(`manual`) 둘 다 허용 | 실내·지하에서 GPS가 안 잡히면 다녀온 사람이 기록을 못 남긴다. 어느 쪽인지는 행에 남긴다 |
| 반경 | **DB에 넣지 않았다** | 몇 m가 맞는지 근거가 없다. 거리를 저장만 하고 판정 기준은 화면 쪽에서 조정한다 |
| 해제 가격 | 30점 | 체크인 1회(10) + 현황 1회(20). "한 곳에서 제대로 기록하면 다른 한 곳이 열린다"가 되도록 |
| 해제 대상 | 다녀오지 않은 장소의 현황 집계 | 다녀온 곳은 직접 봤으니 그냥 열린다. [product-plan-v0.5.md](product-plan-v0.5.md) 오픈 이슈(해제 범위)를 **커뮤니티 열람만**으로 좁혔다 |
| 통화 | KRW 정수 고정, 컬럼명 `amount_krw` | 서울 여행 지출이다. 환율 요구사항이 문서에 없어서 환산을 만들지 않았다. 단위를 컬럼명에 박아 오해를 막는다 |
| 닉네임 | 없음 | 목업의 "가상 닉네임"은 가짜 데이터 생성 지침이고, 실제 닉네임 정책(소유·중복·신고)이 문서에 없다. 집계로 보여주면 닉네임이 필요 없다 |
| 사진 | 없음 | 스토리지 버킷·용량·EXIF·신고·삭제 계약이 없다. 모더레이션 없이 팬 사진 업로드를 켜는 건 되돌리기 어렵다 |
| 자유 텍스트 후기 | 없음 | 위와 같은 이유. [T-015 기록](../tasks/T-015/README.md)도 "후기·댓글은 지금 데이터로는 지어내야 한다"며 제외했다 |

## 7. 아직 없는 것

- **정산(여러 사람 분담).** 어느 문서에도 없고, 여행 그룹·멤버 개념이 아직 없어서 붙일 곳이 없다. 공유 모델이 생긴 뒤에 그 위에 올린다.
- **공유 링크·공동 편집.** 권한 모델(누가 보고 누가 고치나), 만료, 충돌 병합 규칙이 정해지지 않았다. 현재 공유는 [functional-spec.md](functional-spec.md) F-10대로 브라우저에서 만든 PNG를 내보내는 것뿐이다.
- **봇 방어·사용량 제한**, 위치정보법 검토, 수집 목적 고지 문구.

## 8. 적용 절차

기존 테이블과 정책은 건드리지 않는다. 새 파일을 추가만 한다.

1. Supabase SQL Editor에서 `supabase/migrations/202609200002_on_site_records.sql`을 **1회** 실행한다. `202609190001_guest_trips.sql`이 먼저 적용돼 있어야 한다(`public.touch_guest_trip()`을 재사용한다).
2. 실행 후 확인: `place_checkins`·`place_status_reports`·`point_ledger`·`expenses` 4개 테이블, 정책 11개, 함수 6개(`record_checkin`, `record_status_report`, `unlock_place`, `place_status_summary`, `limit_expense_rows`, 그리고 기존 `touch_guest_trip`).
3. 브라우저 두 개(A/B)로 각각 체크인·현황·지출을 남긴 뒤, A가 B의 `owner_id`로 select·insert·update·delete를 시도해 전부 막히는지 확인한다. `point_ledger`에 직접 insert가 거부되는지도 확인한다. 이 확인은 [setup-cloud-trips.md](../setup-cloud-trips.md) 5번과 같은 방식이다.
4. PGlite 검증(12건)은 SQL이 돌아가고 정책이 의도대로 막는다는 것까지만 보증한다. **호스팅된 프로젝트에서의 실제 동작은 3번으로만 확인된다.**
