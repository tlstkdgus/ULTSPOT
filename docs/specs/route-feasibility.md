## 모듈

`src/lib/routing/feasibility.ts`의 `recommendFeasibleRoutes`는 필수 생일카페와 선택 식당/관광지를 구분해 검증된 구간별 이동 추정값으로 최대 3개 대안을 계산한다. 기존 `planTrip`과 UI를 교체하지 않았다.

- 최대 방문 후보 6개, 후보별 날짜 내 운영 구간 최대 2개, 방향별 이동 추정값 1개. 날짜는 호출자가 확정하며 모든 분 단위 값은 그 날짜의 한국 시간이다. 날짜가 다른 자료를 섞지 않는다.
- `required`는 반드시 포함. `eligible=false`인 필수 방문지는 전체 실패하며 조용히 빼지 않는다.
- `windows`는 영업시간·예약 구간·식사 선호 시간의 교집합. 브레이크타임은 분리 구간으로 제공한다. 확정 예약이 없거나 취소/미확인인 장소는 호출자가 eligible=false로 설정한다.
- 방문지 이름 대신 검수된 ID를 사용한다. 출발/도착 ID는 방문 후보 ID와 분리한다. 같은 숙소로 복귀해도 출발/도착 노드 ID를 나눠 제공할 수 있다.
- `legs`는 방향별 이동 분, 적용 가능한 출발 시간 구간, 공급자/근거 이름, 확인 시각. 조회 실패/없는 구간을 0분 또는 고정 45분으로 바꾸지 않는다. 출발 시간 범위를 벗어난 추정값은 사용하지 않는다.
- 체류 전체가 운영 구간에 들어가야 하고 최종 목적지 복귀도 종료 시간 내여야 한다. 일찍 도착한 경우 방문 시작까지 기다린 시간을 포함한다.
- 후보 중 방문 수 우선/이동 최소/일찍 종료 대안을 계산하고 같은 결과는 중복 제거한다. 필수 방문지는 모든 대안에 포함한다.

## 한계와 다음 연결

이 모듈은 **공급자가 제공한 고정 이동시간 스냅샷 안에서의 후보 탐색**이다. 실제 지도/API 조회, 출발 시간별 배차, 교통 변화, 도보 접근성, 비용·예산, OpenAI 호출은 구현하지 않았다. 이동 서비스가 더 넓은 시간대 자료를 갖더라도 이 모듈은 방문 종료 후 일부러 출발을 늦추며 모든 교통편을 탐색하지 않는다. 그래서 전 세계적 최적/실시간 최적 경로로 표현하면 안 된다. 결과는 항상 estimateOnly=true다.

입력 타입은 신뢰 경계를 대체하지 않는다. 외부 JSON/API/OpenAI 출력에는 별도 런타임 스키마 검사, 자료 날짜 대조, 허용 후보 ID 검사와 데이터 최신성 검수가 필요하다. checkedAt은 근거 기록이며 그 자체로 최신성을 보장하지 않는다.

Kiro 연결 순서:
1. 지도/대중교통 공급자 선정과 이용 조건 검토, 주소→좌표 확정, 구간 이동 추정 조회 어댑터.
2. 행사·식당의 날짜별 운영 구간/예약/식사 시간 정규화 어댑터와 외부 입력 검증.
3. 본 모듈에 입력, 실패 시 미확인 구간·조건을 사용자에게 설명. 생일카페/점심 필수를 사용자가 선택하도록 연결.
4. OpenAI는 검수된 후보 ID와 취향을 연결하고 추천 이유를 설명. 출력된 후보/시간은 결정적 검증을 다시 통과시킨다. 모델이 만든 이동시간을 legs로 받지 않는다.
5. 실제 운영 데이터로 통합 테스트 후 기존 엔진을 대체. UI 변경은 Claude/Kiro 담당자 1명만 수행한다.

이 작업은 외부 API 키 없이 검증 가능한 계산 경계를 먼저 구현한 것이며, 현재 서비스가 실제 이동시간으로 추천한다는 의미가 아니다.
